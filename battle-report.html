Preface

On Saturday, June 28th, 2025, I noticed strange activity occurring on my machine. I was quietly working away on some side projects, working with ChatGPT and writing up some code for side projects, one of them being Hexicon. While working on my code I went to look for some music to help me get into flow state (as most developers and programmers do). Since I couldn't find a particular song on Youtube, I went to look for it on SoundCloud. What I noticed was bizarre...SoundCloud, a well known and established website for artists was showing up on Google's seach as not secure. Typically this means that SSL is down, which can happen when SSL keys are in rotation. I figured maybe someone had forgot to rotate the keys and I was looking at a lapse in coverage. Stupid me decided to proceed to the website from the Google search and noticed that the link had redirected me to the actual website. I was not logged on and had no intention of doing so with the website in that state. Doing a little digging ChatGPT informed me that it is strange behavior for Google to actively display an insecure website as the top result for a query. That this could be the result of query poisoning, a common attack surface for hijacking sessions and getting a hold of sensitive session or personal information. After hearing this I went to an online tool that checks a domain name to see is HSTS is active on it. I put in SoundCloud to check if HSTS was active. The online tool verifiedi that there were no problems. That means that for some reason what I was seeing was not what everyone on the internet was seeing. At this time I became more than intrigued, perhaps a little paranoid to the fact that my traffic has now diverted from normal traffic. I closed FireFox right away. After closing FireFox I reopened it. When I reopened it, I saw that not one Window opened, but two. In the preview for the second window that had opened, I could see a webpage active that had CMYK colored barcodes on a blank web page. I closed FireFox again. After consulting with ChatGPT on what it could be, it made sense that my session was likely hijacked, experienced a TLS Session Hijack attack and had bad code infect the browser. Looking at the Event Log on Windows, I noticed that Firefox had complained about COM+ object errors. This stood out to me because to my knowledge Firefox shouldn't have an complaints ith it's COM packages during normal runtime unless something is interfering with them. After doing a little bit of research it was noticed that FireFox has I2C pipes active for error reporting and debugging faults in the application. I quickly theorized that the browser malware may be attempting to attack my OS through these pipes and attempting to run remote COM redirected commands. With my previous limited experience, I remembered that these pipes live in the same space as SQLLocalDB, the MSSQL SQL database. SQL has long been a favored attack vector for bad actors, as the syntax is typically easy to manipulate, stub and cause errors once direct access is provided. I had not considered the database an attack surface for the longest time, because I made sure it was never allowed to connect to the outside world. If an application with access to the outside world was able to become an attack surface though, I could see how transitioning to a local SQL database would allow them to attack permissions and elevate their runtime privileges. I started furiously going through the event logs. This was not new behavior. There was a log trail that corresponded to the actor doing this multiple times, right underneath my nose. Then I saw something in the logs that scared me senseless. The actor left a string phrase that made me understand what they were after. Right there, in the event logs, was a string phrase that directly corresponded to sensitive material I was working on at my current job. My head was spinning, "How could they possibly know about that!?". That shifted my perspective on what I was witnessing occur. My machine was being staged as a contained spill event, where the data being on my machine would make me look suspect of treason. I tried to calm myself as best as I could and attempted to gather more information and understand the mechanism of the attack. I looked through all the COM registries and my System32 files to see if the OS was already compromised. My guess was that hijacking the browser wouldn't be enough to allow them to execute payloads remotely. They had to have some sort of hidden mechanism already on the operating system that was able to collect and process the data they were piping into my system. After scanning System32, COM redirects, CLSIDs and strange tasks that were scheduled I noticed that one library in the System32 directory did not show up on the Windows Appx Manifest. What's worse, is after removing the library I had noticed that sfc /scannow was restoring the library. It is very important to note here, that deleting this library DID NOT TRIGGER A WATCHDOG, BYTE_ISSUE or any other type of blue screen. This was bad, somehow my operating system was treating this library in my System32 as a trusted libary. copyesu. I immediately hashed the library and placed it on a usb for forensice storage. I started grabbing all the logs that I could and evidence of strange activity on my machine. Once I had all the information I started add auditing logs in event viewer to see if I could capture what was using it. After taking ownership I waited to see who would access it. MsiInstaller. What was reponsible for installing packages on my machine was trying to take control of copyesu. I then watched as it did indeed take ownership of the library. Once it took ownership of the library, I ran icacls again to disrupt it. It took ownership back AGAIN. Forensic Analysis

The tools for reverse engineering the attack would be WHISPERFORGE and ARCHER. Both were technically recovered derelicts, but this is exactly why they would be effective. ARCHER is purposefully sabotaged build meant to confuse and deceive the implant USB. The USB would see the Windows hooks to firmware that the OEM BIOS would provide, but there would be no underlying attachment to the kernel which is Linux. In addition to this, with the NVRAM being read-only, I could guarantee whatever persistence the kit might cause, would be wiped away with a power cycle. WHISPERFORGE was not so lucky. My assumption at the time was that if the attacker had left a bad USB behind hoping that I would plug it in to another machine. Another aspect to consider is that there was already a narrative being formed for me on being a witness, that posession of the USB would implicate me as the bad actor and creator of the issue.

After getting ARCHER ready, I secured all the USB ports to read only. I plugged in the one of the USBs, no LED connectivity detected. Good. That's what I would expect from a USB being restricted on a Linux kernel. I started to go through what was left on the USB. Running dd on the USB took an abnormally long time. This type of behavior is consistent with Bad USBs, which hijacks normal read/write paths on the disk to allow for modified behavior. This one however seemed to indicate USB stick embedded firmware corruption. A USB planning to work off of the corrupted sectors on the USB stick or autoplay behavior is typically thwarted by controlling the USB SATA port and disabling those behaviors. This brings us to the other USB. The other USB was active immediately after being plugged in. What do I mean by active? The USB LED indicates activity on the stick to alert uses if writes are being performed. This is done to help users not accidentally remove the USB during a write operation that could leave the USB corrupted. This USB once plugged into the port was glowing red. It's firmware was continuously performing some sort of operations. Worried, I immediately removed the USB stick. I performed some sanity checks to insure I didn't corrupt ARCHER. Sector Based Execution

After pulling the memory, the sectors I could see, 512KB each, were Sectors 0, 1, 2, 6, 7, 8, 12, and 2398. I used a simple bash script to check the usb image:

#!/bin/bash
IMAGE="usb_image.dd"
SECTOR_SIZE=512
SECTOR_COUNT=10000
echo "Scanning $IMAGE for non-zero sectors..."

i=0

while [ $i -lt $SECTOR_COUNT ]; do
sector=$(dd if="$IMAGE" bs=$SECTOR_SIZE skip=$i count=1 status=none | hexdump -v -e '/1 "%02X"')

if [[ "$sector" =~ ^(00)+$ ]]; then
:
else
echo "Sector $i: NON-ZERO"
fi

i=$((i+1))
done

echo "Scan Complete."

This resulted in hexdump files of the all sectors that were found holding binary data. These were the sectors that I mentioned prior. The blobs that were available were run through strings to see if any plain text could be found in the blobs as a starting point.

What Does This Do?

This machine code gets passed into the firmware in the USB chip responsible for reading and writing operations. If modified, it could use the sectors on the USB drive to store execution commands as well as payloads on the device meant to be executed. Each hex code entry corresponds to the location of the instruction in the sector it was found. Though they may be seperated across the entire USB partition, the controller acts as a central location for access to the code and execution of it. There are even jmp commands that act as tripwires for destruction of data on the drive should specific sectors get read. If the controller misses the jump command, the data gets zeroed. This makes it impervious to linear reading algorithms. The only way to get access to the payloads that run is to bypass the USB controller at the hardware level and then use a replacement controller to read what gets zeroed out when tampering.

If we follow the juimp we get down to what looks like the main controller logic for the payload delivery mechanism. A lot of large hex addresses get moved. MSODOS5.0 gets triggered. More bytes get moved. Functions are called with parameters. Then another tripwire is added to start zeroing if somehow the first one wasn't tripped. Here's where things get interesting though...

The USB Landed Into The Board

int 0x13

This is an interrupt. Likely correlating to a system interrupt at a hardware level. By doing this, MSODOS5.0 is able to interrupt the running system and load MSDOS in SMM mode. Somehow this USB is targeting and interrupting a specific service and piece of hardware to insert itself into the system. Not too long after it another block of assembly we see jmp 0xfffffffffaa00402 followed by more function calls. This value is outrageous. The only conceivable way that this is a real number, is that the attacker is calculating the 64^2 approximate location value of a target and is attempting to access it by a buffer overflow attack at the architecture level. There are some other calls later on in the code, but the majority of it is cleanup after execution. This is slick. It operates without permission, it roots into the machine without consent and then sets up the chain for its own persistence.

The Truth Buried In The Code

The code is very complex. At first glance it looks like what you would expect from root and persistance kits, but this was hand crafted for the target, me. The only way the attacker could have calculated the values necessary to land in the locations it needed to set itself would need to be very accurate and planned. This type of attack doesn't just take advantage of hooks left my the firmware, but calculates where it needs to jump to then execute code to inject the malware. On top of that, the attacker took time to add watermarks and taunts to me, not observable unless you are really digging.

0x00000059 382d741eb10b cmp byte [0x0bb11ed3], ch ; [0xbb11ed3:1]=255

It doesn't seem like much at first, but hackers and coders sometimes use a language called 1337-speak. It's a programmatic way for typing number variant characters to express letters. It wasn't until afterwards I would look at my efivars and see in the entries, "GoodNightLed". So this Hex value comparison, probably means, "bye bye little LED." This hex check was likely a way of confirming that the code ran successfully. "Bye bye" in this context, means the malware was installed, the persistance was added and my rig was intended to be dead.

Deeper Down The Rabbit Hole...

From here the only place to go is deeper into the BIOS and the EFI territory. All the EFI indicated that something was booting from the board. EFI redirects allowed whatever was booting to pass through a corrupted UEFI shell to give the root kit access to any kernel that runs. It had masked EFIs present in the EFI directory structure, a 32-bit shell application. EFI's that only appeared to the built-in shell when the net driver running the malware was unloaded in shell. It was and still is, masking system resources by interrupting the handoff to kernel-firmware negotiation steps in the boot process. After exhaustively pouring through all the information available in shell, efi and system utilities a conclusion was drawn. This persistence kit was creating a hypervisor for the kernel to pass through. It's an almost invisible firmware level persistence kit. A user would be none the wiser, thinking a repartition of a drive and a new OS fixed the issue. Even worse it is clearly personally motivated and targeted. Worse, they used tools that weren't theirs.
