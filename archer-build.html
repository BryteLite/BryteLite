ARCHER - The Arch Linux Acer Build

Preface

Following the aftermath of a cyber attack, it was determined that the Windows Cloud Environment had been compromised. With that being said, the artifacts left behind in the wake of the cyber attack needing reverse engineering and documenting. This couldn't be done reliably on a Windows system. The attacker clearly already had the means to intercept multiple attack surface vectors. While the root cause couldn't be established at the time, the prudent thing to do was to create a different environment towards diagnosis, reverse engineering and forensic analysis. The tools: an underpowered Celeron Acer Notebook from 2015, a minimal Arch Linux LIVE USB distro and prayer.

Backstory: Previous Attempts

This was not the first time I had attempted to boot a Linux distro on this machine. In the past I had tried to install Linux Mint and Ubuntu LTE. Both had complications handling the firmware negotiation with the BIOS. It was discovered while playing with the EFI structure of the boot partion that the BIOS, an OEM one, had issues running when using the fallback BOOTX64.EFI that is commonly used for Linux distros. Even after manually making the EFI structure available and double checking grub.efi, grub.cfg and the other distro specific configurations, I would consistently fail to get to kernel. Even after disabling common known issues, like the laptop microphone, intel_audio, bluetooth and shoddy AER (Advanced Error Reporting), nothing would land me into a console or GUI. After some investigation, I noticed that the NVRAM was set to read-only. I then recalled that the laptop came with a preinstalled Windows 10 OS straight from the factory. At this point the lightbulb went off. If the BIOS is having issue negotiating kernel hooks, refuses to boot other distros in secure boot (normal behavior of secure boot) and is not booting from the fallback path, it might be possible that the machine was never intended to boot linux. As limited as my understanding is of UEFI, this is in direct conflict from how UEFI is supposed to function. UEFI is supposed to support the booting of different operating systems and is core-function leveraged in dual-booting. This is when I got an idea of how to take advantage of this design though.

Stage 1: Prepare The Distro

I have had some experiencing with Arch Linux in the past recovering dead or corrupted operating systems. I knew that the distro would be the perfect choice when working in close proximity to the bare metal. Arch is also capable of running completely live, regardless of storage persistence and in RAM. This was going to be ideal for dealing with a non-cooperative BIOS.

Stage 2: Live Booting

Live booting the Arch Distro was fairly straight-forward. Disable Secure Boot (more info on why later), got the BIOS screen and select the USB partition to boot from. This executed without any problems. I still had a problem, NVRAM and my Boot Entries were read-only. This is where my idea comes into play.

Stage 3: Spoofing Windows and Manually Building the Bootloader Config

Stage 4: Lock Down GRUB

The problem with GRUB as a bootloader is that if it's not properly configured, it can be abused. Any EFI can be placed in proximity to GRUB. The GRUB configuration can be altered if not root protected. It was clear that I never had root access on this laptop. The UEFI for the laptop was configured to boot the Windows image that was preinstalled on it and nothing else. This means anyone can do what I did and swap the EFI with their own. This can't be done remotely though. With a BIOS Password in place, locking down the GRUB to only accept allowed images in its config locks down the machine.

Stage 5: Why This Is Good In a Weird Way

I can't stop someone from repeating the steps I took to make Linux work on my machine. Since the BIOS does not give out root-access and restricts booting anything else that isn't Windows, there is no way for someone to perform a boot attack on this machine remotely. This machine can only be root attacked from having physical access to it. Since anyone querying firmware will see a Windows Boot Path, anyone attacking a Linux Kernel will be attempting to attack it from the BOOTX64.EFI path. That fallback is removed after the spoofing and the BIOS will always prefer my spoofed path. If someone wants to corrupt the Windows boot path, they'd need to do it from the Linux fallback, which is second priority. This leaves any boot, rootkit or firmware attack stuck having an existential crisis on what they are exactly. With NVRAM being read-only, there are no other vectors left open. At a glance, my system looks like it points to a Windows Boot Manager. The BIOS even reads the partition and Boot Loader as such. I'm now running a stealth Arch Linux build that appears to be a Windows Boot Path. The only way to change it is to have root level access, which no one does or have physical access and my BIOS password.

Afterthoughts

My original plan for this machine was to use it as a sacrifice to see what the rootkit USB I was left with would do. Running in Arch Linux I was able to monitor the USB, its activity and inspect its contents to understand how it works. I was also able to forensically view both bad USBs to extract their tradecraft secrets and their methodology. I had some concerns understanding about the state of the machine in persitence since I knew this persistence kit worked on my main rig, WHISPERFORGE, and I'm actively hunting it down to extract it. If NVRAM on this laptop is read-only, every single boot is expected to be a fresh run. The attacker would have had no way to make sure any SPI and/or I2C influences he was using would disappear after a power cycle. I'm confident moving forward that this laptop can be used reliably for a long time to come.
